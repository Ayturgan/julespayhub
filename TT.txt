Техническое задание
Название проекта:
QRPayHub — межбанковская платформа для приёма платежей через QR-коды без комиссий.

1. Введение
Создаётся универсальный платёжный сервис, позволяющий любому плательщику, используя мобильное приложение своего банка, оплачивать товары и услуги, сканируя QR-коды, сгенерированные на стороне QRPayHub. При этом исключается комиссия за межбанковские переводы за счёт интеграции платформы с каждым банком-партнёром.

2. Участники системы
Роль
Описание
Плательщик
Физическое лицо, клиент любого банка с мобильным приложением.
Продавец
Юридическое лицо или ИП, предоставляющее услуги или товары.
QRPayHub
Сервис-агрегатор, создающий QR-коды и обрабатывающий платёжные запросы.
Банк
Финансовая организация, владеющая мобильным приложением и счетом клиента.


3. Бизнес-цель
Избежать межбанковских комиссий при оплате между клиентами разных банков путем организации платежей внутри одного банка, через:
интеграцию с банками через API,


направление платежа в банк-эмитент карты/счета клиента,


генерацию защищённой ссылки (QR) с параметрами для конкретного банка.



4. Общая схема взаимодействия
sequenceDiagram
    participant P as Плательщик
    participant App as Мобильное приложение банка
    participant QR as QRPayHub
    participant Bank as Банк получатель
    
    P->>App: Сканирование QR-кода
    App->>QR: GET /payment-info?token=abc123
    QR->>QR: Аутентификация банка по токену/ключу
    QR->>QR: Логирование обращения

    Bank->>QR: POST /payment-status (опционально webhook)
    QR->>QR: Фиксация платежа в биллинге и логах


5. Генерация QR-кода
5.1 Формат QR-кода
QR содержит ссылку на QRPayHub, например:
https://qrpayhub.com/pay?token=abc123xyz

Параметры внутри QR:
Параметр
Назначение
token
Уникальный ID платёжного запроса
redirect_url
(опц.) URL возврата после оплаты


6. Протокол получения информации о платеже
6.1 Запрос от банка:
GET /payment-info?token=abc123
Authorization: Bearer <bank_access_token>
User-Agent: O!Dengi/5.0
X-Device-ID: <device-id>
X-App-Version: 5.3.1

6.2 Ответ от QRPayHub:
{
  "receiver_account": "410019283746501",
  "receiver_bank_code": "B12345",
  "receiver_name": "OsOO MegaShop",
  "description": "Оплата за товар #456",
  "amount": null,
  "currency": "KGS",
  "payment_reference": "QRHUB-456-20250805"
}

amount может быть null, если платёж предполагает ввод суммы вручную (чаще всего).


receiver_bank_code помогает банку определить, что платёж не выходит за пределы банка.



7. Подтверждение и логирование платежа
7.1 Callback (опционально webhook)
После успешного перевода банк отправляет уведомление в QRPayHub:
POST /payment-status
Authorization: Bearer <bank_secret>
Content-Type: application/json

{
  "token": "abc123",
  "status": "success",
  "transaction_id": "TXN098123456",
  "amount": 150.00,
  "payer_phone": "+996700123456",
  "timestamp": "2025-08-05T10:21:00+0600"
}

7.2 Обработка и логирование:
Сервис логирует:
IP, заголовки, User-Agent, банк


параметры токена


дату/время запроса


ответное тело и код


при подтверждении — сохраняет в биллинг: сумма, плательщик, банк, транзакция



8. Безопасность
Аутентификация банка через:


IP whitelist


Access Token / OAuth 2.0 Client Credentials


Подпись (HMAC-SHA256) по определённым полям


QR token должен быть:


UUID + подпись (например, HMAC от содержимого + secret)


иметь TTL (время жизни)


Защита от повторного использования токена:


одноразовый токен или защита от повторной оплаты


Rate Limiting и Throttling:


чтобы банки не спамили /payment-info


Журналирование всего:


попыток получения информации


всех входящих и исходящих транзакций


запросов по ошибке

8.1. Идемпотентность Webhook 
Система должна быть готова к тому, что банк может отправить одно и то же уведомление об оплате несколько раз (например, из-за сетевых проблем). 
Решение: Проверять transaction_id на уникальность. Если транзакция с таким ID уже была успешно обработана, просто возвращать ответ 200 OK, но не проводить операцию повторно.



9. Подводные камни и риски
Риск
Описание и решение
🔴 Межбанк все равно берёт комиссию
Решение — платить внутри банка, для этого нужно сотрудничество с каждым банком.
🔴 QR подделка
Протокол должен проверять подпись токена, TTL, и банку доверять только QR с определённой схемой.
🔴 Отказ банка интегрироваться
Нужно юридически оформлять соглашение с каждым банком.,
🔴 Несовместимость API
Каждый банк может потребовать свою схему интеграции, возможно, придётся поддерживать адаптеры.
🔴 Платёж не завершён
Требуется механизм опроса или webhook от банка (иначе не узнать об успешности).
🔴 Массовая генерация QR-спама
Нужны лимиты, капча и защита от DDoS.


10. Пример использования
Продавец генерирует QR:
Через личный кабинет или API отправляет параметры (название, сумма, описание).


Получает токен + QR-ссылку.


{
  "qr_url": "https://qrpayhub.com/pay?token=abc123",
  "expires_in": 600
}

Покупатель:
Сканирует QR в приложении банка.


Приложение делает запрос, получает данные, отправляет платёж, уведомляет QRPayHub.
